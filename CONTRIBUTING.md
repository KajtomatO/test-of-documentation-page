# Updating the documentation

This file explains how to change the site: writing pages, previewing them,
versioning, publishing and upgrading. For one-time GitHub settings see
[SETUP.md](SETUP.md).

## Local development

Requirements: Node 24 (`.nvmrc`; any Node 20+ works) and npm.

```bash
npm ci            # install exactly the versions from package-lock.json
npm start         # dev server with live reload, opens http://localhost:3000/test-of-documentation-page/
npm run build     # production build into build/ (this is what CI runs)
npm run serve     # serve build/ locally
npm run typecheck # TypeScript check of config and React components
npm run clear     # delete caches when the dev server shows stale content
```

Two things behave differently in `npm start` than on the published site:

- **Search does not work in the dev server.** The search index is generated at
  build time. To try it, run `npm run build && npm run serve`.
- **Broken links only fail `npm run build`.** The dev server shows a warning
  in the terminal; the production build (and therefore CI) aborts.

## The everyday change

1. Create a branch.
2. Edit or add Markdown files (see the next sections for *where*).
3. Check the result with `npm start`, then run `npm run build` once to catch broken links.
4. Open a pull request. The **test-build** check must pass.
5. Merge to `main`. The **Deploy to GitHub Pages** workflow publishes the site,
   usually within two to three minutes. Watch it in the **Actions** tab.

Nothing is deployed from branches or pull requests, only from `main`.

## Where content lives: the versioning rule

The site has two documentation versions, and they are stored in different
folders. Editing the wrong one is the most common mistake.

| Folder | Version | Published at | Who sees it |
| --- | --- | --- | --- |
| `docs/` | **Next** (unreleased) | `/docs/next/` | Only people who pick "Next" in the version dropdown |
| `versioned_docs/version-1.0/` | **1.0** (latest release) | `/docs/` | Everyone by default |

Consequences:

- **A fix that current readers should see** (typo, wrong command, missing
  step) goes into `versioned_docs/version-1.0/`.
- **Documentation for something not yet released** goes into `docs/`.
- **A fix that applies to both** must be made in both files. There is no
  automatic sync.
- `versioned_docs/version-1.0/` is a plain copy of `docs/` at the time version
  1.0 was cut. Edit it directly; it is not generated.

The Webhooks guide is an example of a Next-only page: it exists in
`docs/guides/webhooks.md` but not under `versioned_docs/`.

## Adding a page

Create a Markdown file in the right folder. Front matter controls its
position and metadata:

```md
---
sidebar_position: 3
title: Retries and backoff
description: Shown in search results and social previews.
---

# Retries and backoff
```

- The sidebar is **generated from the folder structure** (`sidebars.ts` only
  says `autogenerated`). Files are ordered by `sidebar_position`, then by name.
- Folders become collapsible categories. Each folder has a `_category_.json`
  that sets its label and position, for example `docs/guides/_category_.json`.
- Use `.md` for plain Markdown. Use `.mdx` only when the page imports React
  components (see `docs/getting-started/installation.mdx` for tabs).
- To make a page the landing page of a version, give it `slug: /`
  (see `docs/intro.md`).

## Links and images

- Link to other pages by **relative file path**, including the extension:
  `[Quickstart](./getting-started/quickstart.md)`. Docusaurus rewrites the
  link and validates it. The build fails on a broken link, which is intended.
  Relative links also keep working when the file is copied into a versioned
  snapshot.
- Do not link to a page in another version by URL unless you mean it.
- Put images that belong to one page next to it and reference them
  relatively: `![Run lifecycle](./img/run-lifecycle.png)`. Images stored this
  way are snapshotted together with the docs when a version is cut.
- Put site-wide assets (logo, favicon) in `static/img/` and reference them as
  `/img/logo.svg`; Docusaurus prepends the base URL automatically.

## Markdown features used on this site

| Feature | Syntax | Example page |
| --- | --- | --- |
| Hints (admonitions) | `:::tip` … `:::`; with a title: `:::tip[Requirements]` … `:::`. The title **must** be in square brackets, `:::tip Requirements` renders as plain text | `docs/guides/defining-jobs.md` |
| Code block title and line highlight | ```` ```yaml title="jobs/hello.yaml" {1,3} ```` | `docs/getting-started/quickstart.md` |
| Tabs | `import Tabs from '@theme/Tabs'` in an `.mdx` file | `docs/getting-started/installation.mdx` |
| Mermaid diagram | ```` ```mermaid ```` fenced block | `docs/guides/architecture.md` |
| Tables | GitHub-flavoured Markdown tables | `docs/reference/cli.md` |

Mermaid diagrams are rendered in the browser and follow the light/dark theme.

Markdown files are processed as MDX. Two characters have special meaning
outside code blocks and must be escaped or wrapped in backticks:
`{` `}` (JavaScript expression) and `<` (JSX tag). Writing `<name>` in prose
breaks the build; write `` `<name>` `` instead.

## Cutting a new version

Do this when a release ships and the content in `docs/` should become the
default for readers.

```bash
npm run docusaurus -- docs:version 1.1
```

This copies `docs/` to `versioned_docs/version-1.1/`, copies the sidebar to
`versioned_sidebars/version-1.1-sidebars.json`, and prepends `"1.1"` to
`versions.json`. The newest entry in `versions.json` becomes the default at
`/docs/`; older versions move to `/docs/1.0/`. No change to
`docusaurus.config.ts` is required.

Commit all three generated locations. After this, `docs/` is the future 1.2.

To **remove** a version, delete its folder under `versioned_docs/`, its file
under `versioned_sidebars/`, and its entry in `versions.json`.

To change the dropdown label or the "unreleased" banner of a version, edit
`presets[0].docs.versions` in `docusaurus.config.ts`.

Each extra version increases build time and the search index. Keep only
versions that readers still use.

## Changing the site itself

| Change | File |
| --- | --- |
| Title, tagline, navbar, footer, GitHub links | `docusaurus.config.ts` |
| Colours, fonts, spacing, component styling | `src/css/custom.css` |
| Hint (admonition) markup | `src/theme/Admonition/Types.tsx` |
| Landing page text and feature cards | `src/pages/index.tsx`, `src/components/HomepageFeatures/index.tsx` |
| Logo, favicon, social card | `static/img/` (`logo.svg`, `favicon.svg`) |
| Search behaviour | the `@easyops-cn/docusaurus-search-local` entry in `docusaurus.config.ts` |

Run `npm run typecheck` after editing TypeScript files; CI runs it too.

## The theme

The look is modelled on GitBook's default ("clean") theme: Inter for text,
IBM Plex Mono for code, a purple accent, white surfaces, small corner radii,
flat tinted hint boxes and bordered code blocks. It is implemented without a
third-party theme, so upgrades of Docusaurus do not depend on anyone else.

- **Colours** are 12-step scales named `--gb-tint-*` (neutral), `--gb-primary-*`
  (accent) and `--gb-info/success/warning/danger-*` at the top of
  `src/css/custom.css`, once for light mode and once under
  `[data-theme='dark']`. To re-brand, change those values; everything else
  refers to them. Infima variables (`--ifm-*`) are mapped onto the scales in
  the next block, followed by per-component overrides.
- **Fonts** are bundled from npm (`@fontsource-variable/inter`,
  `@fontsource/ibm-plex-mono`) and loaded through `clientModules` in
  `docusaurus.config.ts`. No request goes to Google Fonts at runtime. To swap a
  font, install another `@fontsource` package, change the two `clientModules`
  entries and the `--ifm-font-family-*` variables.
- **Hints** are rendered by a swizzled component, `src/theme/Admonition/Types.tsx`,
  which replaces Docusaurus's default admonition layout (uppercase title on
  top) with an icon column and an optional bold title. The five types map to
  the semantic colour scales. Because this file overrides a theme internal,
  check it still compiles after a Docusaurus major upgrade (`npm run typecheck`).
- **Code block backgrounds** are set in the `prism` section of
  `docusaurus.config.ts`; token colours come from the stock `github` and
  `dracula` Prism themes.
- **Logo and favicon** are small inline SVGs in `static/img/`. Replace them with
  your own; `favicon.svg` may also be swapped for a `.ico` or `.png` by changing
  `favicon` in `docusaurus.config.ts`.

There is no visual regression test. After changing the theme, look at the
landing page, a docs page with a code block, a hint and a table, the version
dropdown, and both colour modes.

## Upgrading dependencies

- **Docusaurus:** all `@docusaurus/*` packages (including `theme-mermaid`)
  must have the same version. Bump them together, then run `npm run build`
  and read the [release notes](https://github.com/facebook/docusaurus/releases)
  for breaking changes:

  ```bash
  npm install @docusaurus/core@latest @docusaurus/preset-classic@latest \
    @docusaurus/theme-mermaid@latest @docusaurus/faster@latest \
    @docusaurus/module-type-aliases@latest @docusaurus/tsconfig@latest \
    @docusaurus/types@latest
  ```

- **Search plugin:** `npm install @easyops-cn/docusaurus-search-local@latest`,
  then `npm run build && npm run serve` and try a search.
- **Node:** change `.nvmrc`. Both workflows read the version from that file.
- **GitHub Actions:** bump the `uses:` versions in `.github/workflows/*.yml`.
  The deploy workflow's `upload-pages-artifact` and `deploy-pages` majors are
  released together; keep them in step.

## What never goes into git

`node_modules/`, `build/` and `.docusaurus/` are generated and ignored. If a
build seems wrong, `npm run clear` removes the caches.
